# iOS UI tests

Four XCUITests that drive iOS, not the app. Everything the app itself can be
driven through lives in `.maestro/flows`, which also covers Android; this
target exists only for the things outside Maestro's reach.

```bash
bun run test:e2e:ios:ui
```

It needs a booted simulator, a built app (`bun run preview:ios:local`) and the
dev server. `E2E_EMAIL` / `E2E_PASSWORD` are the seeded staging account from
`database/seeders/UserSeeder.ts`; without them the signed-in test skips itself.

| Variable | |
| --- | --- |
| `IOS_SIMULATOR` | Name or UDID, when more than one is booted |
| `IOS_UI_KEEP_STATE` | `true` leaves the installed app and its keychain alone |
| `IOS_BUNDLE_ID` | Defaults to `org.wildloop.app` |

## What it covers

The account gate, from outside the app: a cold launch meets it, it survives a
trip to the home screen and back, it raises no location prompt, and Record
raises one as soon as somebody signed in opens it.

The last two are a pair, and they are the reason this target exists. A unit
test can say the bundle did not ask for a position; only a device can say iOS
did not put a permission dialog on the screen. That dialog over somebody's
feed is what 04d2eec7 fixed.

## Why a separate Xcode project

Craft regenerates `storage/framework/mobile/ios` from its own template on
every `build:ios`, filling the target list from its config — there is no hook
for one of ours, so a test target added there is gone on the next build. This
project never builds Wildloop. The tests attach to whatever is installed, by
bundle id, which is also what lets the same suite run against a phone.

`WildloopUITests.xcodeproj` is generated by the runner and git-ignored. Edit
`project.yml`.

## Two things that cost a day to find

**`TEST_RUNNER_<VAR>` reaches nothing here.** It is the documented way to pass
environment into a test runner, and in a UI test bundle with no host app the
runner process saw none of it — measured by dumping
`ProcessInfo.processInfo.environment`. The credentials travel through the
scheme instead, substituted by xcodegen as it writes the project.

**An unset variable substitutes to an empty string, not to nothing.** So
`environment["X"] ?? "default"` takes the empty string, and the app launches
by a bundle id of `""`. That fails as `FBSApplicationLibrary returned nil for
""`, which names nothing. `Wildloop.value(of:)` treats empty as absent.

## How long it takes

About 50 seconds of tests, plus a reinstall and an xcodebuild. One run of the
signed-in test took 735 seconds instead of its usual 22 — the step it sat on
was the Record screen arriving, so the likely cause is the dev server
compiling a route rather than anything in the test. Worth knowing before you
assume a hang: let it finish once before killing it.

## What it cannot cover

The home-screen long-press menu, which is where the App Shortcut leak closed
in 14245c1b came through. Neither stx's native runtime nor craft-native has a
Shortcuts module, so `craft.shortcuts` does not exist in an all-native build
and nothing registers the quick actions — `registerAppShortcuts` answers
`unsupported`, correctly. Siri and Spotlight are unaffected: those come from
the App Intents Craft generates out of `config/mobile.ts`.
